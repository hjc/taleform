One approved PRD, split into slices, for rebuilding Taleform on a declarative model: a glossary of core concepts; a YAML model config that defines composable, extensible data elements (Mission, Act, Beat, Encounter, NPC, Arc, Campaign and whatever a DM adds); a default config shipped with the plugin; the six builders rewritten to read that config; and a plugin view in Obsidian that shows the model in use. Hand-off: prd-writing, then the slices stack on hjc/map--generic-data-model.

Completion bar. The developer approves a PRD whose slices, once built, reproduce today's test-vault/ output byte for byte from the shipped default config, with every hard-coded convention moved into that config or written down as a fixed contract.

Standing constraints. What holds for the whole effort, whoever is working it.

ConstraintConsequence
The shipped default config reproduces today's generated output exactly; output changes come afterwards, as config edits.Without it there is no proof the config expresses what the code did, and every DM's vault churns on upgrade.
Arcs and Campaigns are modelled and shown in the view, but no Arc or Campaign Map builder is built.Building them here doubles the destination; they are the first features on the new model, on the roadmap.
The config is plain YAML in its first cut, readable and editable by a human or Claude without tooling.A bespoke language before the need is proven costs the editability that is the point.
The five invariants in CLAUDE.md hold throughout; above all, builders never write frontmatter.A build that feeds back into its own input, or touches the DM's text.
src/core/ stays free of Obsidian imports; both runners read the same config.The CLI and the hooks stop working headless.
Probes and tasks write only to a scratch copy of test-vault/, never a DM's vault.Edits to a DM's real campaign.
